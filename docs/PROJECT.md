## Что за проект

**Название:** WMS Geology

**Зачем:** Управление складским хранением геологических материалов
(проб, керна). Закрывает: отсутствие БД, поиск, наряд-задания,
QR-идентификацию, адресное хранение, отчётность, миграцию
существующих запасов.

**Для кого:**
- Менеджеры (создание Н/З, аналитика, отчёты).
- Рабочие / кладовщики (приёмка, выдача, инвентаризация, перемещения).
- Администраторы (пользователи, топология склада, БД).

**Что делает:** Единая база данных + веб-приложение (Windows/браузер) +
Android-приложение для планшетов. QR-коды как основной идентификатор
тары и ячеек. Адресное хранение: комната → стеллаж → пролёт → ярус →
ячейка → поддон → тара → проба.

## Особенности

### Фазы проекта

Проект проходит две фазы:

1. **Проектная фаза** — сейчас. Артефакт захода — **документы**
   (`DATABASE.md`, `API.md`, `SCENARIOS.md`), а не код. Тесты
   не пишутся. Цикл «норм» действует.
2. **Кодовая фаза** — начинается после утверждения схемы БД,
   API-контрактов и сценариев приёмки. Артефакт захода — код +
   тесты. Обычные правила `RULES.md`.

**Текущая фаза:** проектная.

### Проектные заходы

Заход в проектной фазе отличается от кодового:

- Артефакт: 1 документ в `docs/`.
- Ветка: `docs/<имя>`.
- Тесты не требуются.
- «Норм» — ревью документа пользователем.
- Merge: в `feature/...` или сразу в `main` (для базовых доков).

### Внешние интеграции

Лаборатории (несколько) — источники данных. Формат обмена на первом
этапе — **Уровень 1 (наклейка поверх)**. Позже — Уровень 2 (генератор
этикеток как сервис для лабораторий).

### QR-стратегия

- Основной QR — на **таре**.
- На пробах — опционально (поле в `Samples` есть).
- Существующие этикетки не переклеиваются. Старый ID хранится
  в `Samples.legacy_data` (JSONB).

### Домен (ключевое)

- **Проба** — физическая единица хранения (`Samples`). Не делится
  внутри WMS.
- Разделение по типам исследования происходит **вне системы**
  (в лабораториях).
- Одна тара = **один** тип исследования.
- Номер пробы может повторяться.
- Наряд-заказ: `INCOMING` ↔ `CODED`, связь через `linked_order_id`.
- Проба ↔ Н/З: many-to-many через `SampleWorkOrders`.

## Проектные правила (дополняют `RULES.md`)

1. **Проектная фаза.** Пока не утверждены `DATABASE.md` и `API.md` —
   код не пишем. Артефакт захода = документ.
2. **Переключение фаз** — решением в `DECISIONS.md`.
3. **Схема БД меняется** только через миграцию + обновление
   `DATABASE.md` в том же заходе.
4. **API меняется** только через обновление `API.md` в том же заходе.
5. **Архитектурные решения** фиксируются в `DECISIONS.md` до реализации.
6. **Файлы доков** выдаются единым блоком (для удобного копирования).
