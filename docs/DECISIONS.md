### 1.1. 2026-10-07

Читается одинаково на русском и английском.

**Где:** `README.md`, `PROJECT.md`.

**Статус:** ✅ действует.

### 1.2. 2026-10-07

#### Стек технологий

**Решение:**
- БД: PostgreSQL 16+.
- Бэкенд: Python 3.12 + Django + DRF.
- Мобильное: Flutter (Android-планшет).
- Веб: React + TypeScript.

**Причина:**
- PostgreSQL — стандарт для WMS с большими объёмами, JSONB для
  `legacy_data`, готовность к PostGIS в будущем.
- Python/Django — быстрый старт, встроенная админка, экосистема
  для QR-генерации и OCR.
- Flutter — единый код для Android, производительность, работа
  с камерой.
- React — гибкость, много UI-библиотек.
- Все компоненты — под MIT/Apache/BSD → свободно для коммерции.

**Где:** `PROJECT.md` §Стек.

**Статус:** ✅ действует.

### 1.3. 2026-10-07

#### Схема наряд-заказов — self-reference (Вариант A)

**Решение:** `WorkOrders` содержит поле `linked_order_id`
(self-reference). Типы: `INCOMING` и `CODED`.

**Причина:**
- Один входящий может быть связан с несколькими кодированными
  и наоборот.
- Вариант с двумя колонками (`incoming_number`, `coded_number`)
  не масштабируется при появлении третьего типа.
- Self-reference честно отражает реальность.

**Где:** `docs/DATABASE.md`.

**Статус:** ✅ действует.

### 1.4. 2026-10-07

#### Проба как единица хранения

**Решение:** `Samples` — физическая единица хранения. Одна строка =
одна проба с конкретным типом исследования в конкретной таре.
Таблица `SampleParts` **не создаётся**.

**Причина:**
- Разделение проб по типам происходит **вне WMS** (в лабораториях).
- WMS получает уже разделённые пробы и фиксирует реальность.
- Тип исследования — ключевой критерий поиска.

**Где:** `docs/DATABASE.md`, `PROJECT.md` §Домен.

**Статус:** ✅ действует.

### 1.7. 2026-10-07

#### Связь проба ↔ наряд-заказ через `SampleWorkOrders`

**Решение:** связь M:N через `SampleWorkOrders`.
`Samples.current_work_order_id` хранит только актуальный Н/З.

**Причина:**
- Проба относится **и к входящему, и к зашифрованному** Н/З.
- Пользователь должен фильтровать по любому из них и получать
  одинаковый набор проб.
- M:N покрывает случай участия пробы в нескольких Н/З.

**Где:** `docs/DATABASE.md`.

**Статус:** ✅ действует.

### 1.8. 2026-10-07

#### QR-стратегия

**Решение:**
- Основной QR — на **таре**.
- На пробах — опционально.
- Существующие этикетки не переклеиваются. Старый ID хранится
  в `Samples.legacy_data` (JSONB).

**Причина:**
- Тара — внешняя единица при перемещениях.
- Сканирование тары даёт доступ ко всем пробам внутри.
- Миграция — «наклейка поверх».

**Где:** `docs/DATABASE.md`, `PROJECT.md` §QR-стратегия.

**Статус:** ✅ действует.

### 1.9. 2026-10-07

#### Интеграция с лабораториями — Уровень 1 на старте

**Причина:**

## 2. Что не делаем и почему

- **Не используем `SampleParts`.** Разделение — вне WMS (см. 1.4).
- **Не храним две колонки для Н/З.** Не масштабируется (см. 1.3).
- **Не заставляем лаборатории использовать наш формат этикеток
  на старте.** Долгие согласования (см. 1.9).
- **Не переклеиваем существующие этикетки.** Остановка склада
  (см. 1.8).
- **Не используем закрытые лицензии в ядре.** Требование
  коммерциализации.

## 3. Глоссарий

### Данные

| Термин | Что значит |
|---|---|
| **Проба (Sample)** | Физическая единица хранения. Пара (номер пробы, тип исследования) в конкретной таре. |
| **Наряд-заказ (Н/З, WorkOrder)** | Группа проб. Тип `INCOMING` или `CODED`. |
| **Входящий Н/З** | Название Н/З до шифровки. Тип `INCOMING`. |
| **Зашифрованный Н/З** | Название Н/З после шифровки. Тип `CODED`. |
| **Тип исследования** | Ключевой критерий классификации (шлифы, химия, изотопы). |
| **Тара (Container)** | Физический контейнер. Пробы одного типа. |
| **Поддон (Pallet)** | Платформа для тар. В ячейке или на полу. |
| **Ячейка (Cell)** | Слот на ярусе. Вмещает до 3 поддонов. |
| **Адрес** | Комната / Стеллаж / Пролёт / Ярус / Ячейка. |
| **Участок (Site)** | Место отбора проб. |
| **Скважина (Well)** | Источник пробы: номер, месторождение, куст. |

### Процесс

| Термин | Что значит |
|---|---|
| **Шифровка** | Присвоение Н/З нового названия после лабораторной обработки. |
| **Приёмка** | Поступление тары с пробами: скан → записи → размещение. |
| **Размещение** | Привязка тары к ячейке/поддону/полу. |
| **Перемещение** | Изменение адреса тары внутри склада. |
| **Инвентаризация** | Сверка физического наличия с системой. |
| **Наряд-задание** | Рабочее задание кладовщику: найти, переместить, выдать, проверить. |
| **Жизненный цикл** | История пробы: от приёмки до выдачи/утилизации. |

### UI

| Термин | Что значит |
|---|---|
| **Дашборд** | Главный экран с виджетами и быстрыми действиями. |
| **Сканер** | Экран мобильного приложения для распознавания QR. |
| **Sidebar** | Боковое меню навигации. |
| **Панель быстрого доступа** | Плитки-кнопки на дашборде. |

## 4. Что НЕ значат эти термины

- «**Часть пробы**» — не используется в WMS.
- «**Ячейка**» — не одно место для поддона. Слот на **до 3 поддонов**.
- «**Наряд-заказ**» — не одна строка. Входящий и зашифрованный —
  **разные строки**, связанные через `linked_order_id`.
- «**Проба**» — не уникальна по номеру. Уникальна по `sample_id`.
