### 1.20. 2026-10-07 — Топология склада: 4 яруса A–D, 1 поддон в ячейке

**Решение:**

Иерархия хранения:
Комната
└── Стеллаж
└── Секция (пролёт)
├── Ярус A (level 1, нижний)
│ ├── Ячейка 1 → 1 поддон → N тар → M проб
│ ├── Ячейка 2 → 1 поддон → N тар
│ └── Ячейка 3 → 1 поддон → N тар
├── Ярус B (level 2)
├── Ярус C (level 3)
└── Ярус D (level 4, верхний)

Напольное хранение (в комнате):
├── Поддон → N тар
└── Тара напрямую → M проб

text

- **Ярусов — ровно 4** (A, B, C, D), маркируются буквами снизу вверх.
- **Ячеек на ярусе — 3.**
- **В ячейке — ровно 1 поддон.**

**Причина:**
- Соответствует физической планировке склада.
- Буквенная маркировка A–D удобнее числовой (1–4) — совпадает с маркировкой на стеллажах.

**Где:** `backend/apps/storage/models.py`, `docs/DATABASE.md`.
**Статус:** ✅ действует.

### 1.21. 2026-10-07 — `Pallet` — «тихий» объект (Вариант A)

**Решение:** модель `Pallet` **остаётся** в БД, но:

- **Нет QR-кода** — физически на поддоне его нет.
- **Нет пользовательского `pallet_code`** — генерируется автоматически, не показывается.
- **Нет `position_in_cell`** — ячейка содержит ровно 1 поддон.
- **`cell` → OneToOneField** (1 ячейка = 1 поддон).
- **`capacity_override`** — JSONB с переопределением вместимости на конкретном поддоне.

**Причина:**
- Пользователь: *«информация о хранении живёт в ячейке, поддон — физический носитель, но он мобилен»*.
- Одна атомарная операция «переместить поддон» = `Pallet.cell` меняется → все тары «уезжают» вместе (их FK на поддон не меняется).
- Модель остаётся, потому что при перемещении важно, что «поддон уехал целиком, вместе с тарами».

**Где:** `backend/apps/storage/models.py`.
**Статус:** ✅ действует.

### 1.22. 2026-10-07 — QR-стратегия: только секция, ячейка, тара

**Решение:** QR-коды навешиваются на:

| Объект | QR | Назначение |
|---|---|---|
| Комната | ❌ | Не нужен |
| Стеллаж | ❌ | Не нужен |
| **Секция (пролёт)** | ✅ | Виртуальный вид всех ярусов A–D и ячеек. Работа с высоты без лазания. |
| **Ячейка** | ✅ | Точечная работа, точное размещение |
| ~~Поддон~~ | ❌ | Физически нет |
| **Тара** | ✅ | Приёмка, выборка, инвентаризация |
| Проба | ❌ | Не клеим в MVP |

**Причина:**
- На поддонах физически нет QR.
- На пробах — не клеим, идентифицируем через тару.
- Секция + ячейка дают двухуровневый доступ: грубый и точный.

**Payload QR:**
- Секция: `WMSG:SECTION:<section_id>`
- Ячейка: `WMSG:CELL:<cell_id>`
- Тара: `WMSG:CONTAINER:<container_id>`

**Где:** `docs/DATABASE.md`, `docs/SCENARIOS.md`.
**Статус:** ✅ действует.

### 1.23. 2026-10-07 — Выборка: `PickList` + `PickListItem` + `Shipment`

**Решение:** три модели.

**`PickList`** — список выборки:
- `pick_list_number` (номер, например «В-2026-001»),
- `created_by`, `created_at`,
- `status`: `DRAFT` / `ACTIVE` / `COMPLETED` / `CANCELLED`.

**`PickListItem`** — строка списка:
- FK на `PickList` и `Sample`,
- `status`: `PENDING` / `PICKED` / `NOT_FOUND` / `SENT`,
- `picked_at`, `picked_by`, `note`.

**`Shipment`** — отправка в лабораторию:
- `shipment_number`, `destination`, `sent_at`, `sent_by`,
- M:N с `Sample` (или FK на `PickListItem`).

**Причина:**
- Выборка — уровень **пробы**, не тары. Извлекают пробу, тара остаётся.
- Отдельный `Shipment` даёт: сопроводительные документы, отчёт «что куда уехало».
- Один список может дать пробы в несколько отправок и наоборот.

**Где:** новое приложение `apps/picking/`.
**Статус:** ✅ действует.

### 1.24. 2026-10-07 — Утилизация: soft-delete

**Решение:** проба не удаляется физически. Статус `DISPOSED` + поля:

- `Sample.disposed_at` — когда,
- `Sample.disposed_by` — кто,
- `Sample.disposal_reason` — причина.

Активные запросы фильтруют `WHERE status != 'DISPOSED'`.

**Причина:**
- Трассируемость важнее места: история жизни пробы сохраняется.
- Может понадобиться отчёт «что утилизировано за период».
- Физическое удаление = потеря данных навсегда.

**Где:** `backend/apps/samples/models.py`.
**Статус:** ✅ действует.

### 1.25. 2026-10-07 — Пул перемещений: `MoveOperation` (голова + строки)

**Решение:** две модели.

**`MoveOperation`** — операция перемещения:
- `operation_number`,
- `target_cell` (или `target_floor_room`),
- `created_by`, `created_at`, `completed_at`,
- `status`: `DRAFT` / `IN_PROGRESS` / `COMPLETED` / `CANCELLED`.

**`MoveOperationItem`** — строка:
- FK на `MoveOperation`,
- FK на `Pallet` (основной случай) или `Container` (если перемещается тара отдельно),
- `source_cell` — на момент добавления в пул,
- `status` — `PENDING` / `MOVED` / `SKIPPED`.

**Как работает (пользовательский сценарий):**
1. Рабочий открывает «Новое перемещение».
2. Сканирует ячейку 1 → приложение: «Добавить поддон в пул?» → Да.
3. Сканирует ячейку 2 → то же.
4. Указывает целевую ячейку.
5. Нажимает «Выполнить» → все поддоны переезжают разом.
6. Одна запись в `AuditLog` — одна операция, N объектов.

**Причина:**
- Меньше действий рабочему.
- Одна запись в журнале = проще откатить.
- История перемещений: отчёт «кто, что, куда, когда».

**Где:** новое приложение `apps/movements/` или в `apps/storage/`.
**Статус:** ✅ действует.

### 1.26. 2026-10-07 — Вместимость: через тип тары + override на поддоне

**Решение:** вместимость — свойство **поддона**, определяется через тип тары.

```python
class ContainerType:
    name = "Коробка малая", "Ящик", ...
    size_class = "S", "M", "L"
    max_on_standard_pallet = IntegerField(default=10)
    is_core = BooleanField(default=False)

class Pallet:
    cell = OneToOneField(Cell)
    pallet_type = "STANDARD" / "CORE"
    capacity_override = JSONField(default=dict)
    # например: {"small_box": 15, "big_box": 6}

class Container:
    container_type = FK(ContainerType)
Логика проверки при размещении тары:

Текущее содержимое поддона → количество тар каждого типа.

Лимит: Pallet.capacity_override[type] ИЛИ ContainerType.max_on_standard_pallet.

Override в приоритете.

Превышение — предупреждение рабочему (не блокировка).

Если рабочий подтверждает — запись в AuditLog.

Причина:

Реальные размеры тары разные, единое число на ячейку не работает.

Override на поддоне даёт гибкость без пересоздания типа.

Предупреждение вместо блокировки: физическая реальность важнее модели.

Где: backend/apps/storage/models.py.
Статус: ✅ действует.

1.30. 2026-10-07 — Помощник по сортировке: 4 функции в MVP
Решение: в MVP помощник по сортировке делает:

Рекомендация ячейки для готового поддона.
Рабочий собрал поддон → «Куда поставить?» → top-5 ячеек с обоснованием.

Рекомендация ячейки для одиночной тары.
Рабочий в приёмке → сканирует тару → система: «Положить на поддон в ячейке X — там 3 тары с того же участка».

Раскладка пула тар по N поддонам.
Рабочий указал N (например, 2) и отсканировал тары → система: «Поддон 1 — эти тары, Поддон 2 — эти».

Критерии (по убыванию важности):
участок → наряд-заказ → тип исследования → соседние номера тар.

Что НЕ делает в MVP:

Учёт веса и объёма.

Автоматический подбор N поддонов.

Bin packing (оптимальная упаковка).

Маршрут обхода склада.

Что уходит в серию 2.0:

Автоопределение N поддонов.

Bin packing.

Маршрут обхода.

Учёт веса/объёма.

Причина:

Простой уровень решает 60% боли рабочего.

Bin packing — NP-трудная задача, требует данных.

Лучше накопить данные и понять, что реально полезно.

Где: сервисный слой apps/sorting/ (появится в серии 1.1 или 1.2).
Статус: ✅ действует.
