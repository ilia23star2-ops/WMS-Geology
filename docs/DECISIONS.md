### 1.14. 2026-10-07 — Портативный PostgreSQL вместо установки

**Решение:** используем **портативный PostgreSQL**, развёрнутый
в `D:\Dev\pgsql\`, вместо:
- Локальной установки PostgreSQL (требует прав администратора).
- Docker Desktop (требует прав администратора и ~500 МБ).
- SQLite (не потренируем JSONB, GIN-индексы).
- Облачного PostgreSQL (интернет-зависимость).

**Причина:**
- Нет прав администратора.
- Полноценный PostgreSQL: JSONB, индексы, транзакции.
- Полная изоляция: всё в одной папке.
- Совместимость с CI.

**Ограничения:**
- Локаль кластера — `Russian_Russia.1251`.
- Сервер не является службой Windows — запускается вручную.

**Где:** `backend/.env`, `CONTEXT.md` §PostgreSQL.
**Статус:** ✅ действует.

### 1.15. 2026-10-07 — Все Django-команды через `poetry run`

**Решение:** запускать `manage.py` и Python-скрипты только через
`poetry run python ...` из терминала.

**Причина:**

- `poetry run` гарантированно использует venv проекта.

**Где:** `PROJECT.md` §Команды.

### 1.16. 2026-10-07 — Кастомная модель User не создаётся

**Решение:** используем **стандартную** `django.contrib.auth.User`
+ расширение `UserProfile` через OneToOne.

**Причина:**
- `auth_user` уже создан миграциями Django.
- Кастомный User потребовал бы пересоздать кластер БД или
  сделать сложную миграцию `AUTH_USER_MODEL`.
- Стандартные поля (`username`, `first_name`, `last_name`,
  `is_active`, `is_staff`, `is_superuser`) достаточны.
- Роль и ФИО — в `UserProfile`, доступ через `user.profile`.

**Где:** `backend/apps/users/models.py`.
**Статус:** ✅ действует.

### 1.17. 2026-10-07 — Роли: seed-команда вместо фикстур

**Решение:** роли (`admin`, `manager`, `worker`) создаются
management-командой `python manage.py seed_roles`. Команда
идемпотентна.

**Причина:**
- Django fixtures (JSON/YAML) неудобны в поддержке.
- Management-команда легко вызывается и в проде, и в CI.
- Идемпотентность: можно запускать сколько угодно раз.

**Где:** `backend/apps/users/management/commands/seed_roles.py`.
**Статус:** ✅ действует.

### 1.18. 2026-10-07 — `Pallet` может быть «в пути» (все NULL)

**Решение:** CHECK-constraint `pallet_location_exclusive` допускает
три состояния:
- в ячейке (`cell` + `position_in_cell`);
- на полу (`floor_room`);
- **«в пути»** (все три поля NULL).

**Причина:**
- Поддон физически может быть перемещён, а адрес ещё не назначен.
- При загрузке в приёмке/перемещении нужен промежуточный статус.
- Строгая XOR ломала бы сценарий.

**Где:** `backend/apps/storage/models.py`.
**Статус:** ✅ действует.

---

### 1.19. 2026-10-07 — `Container` использует `PROTECT` при удалении

**Решение:** `Sample.container` использует `on_delete=PROTECT` —
нельзя удалить тару, пока в ней есть пробы.

**Причина:**
- Защищает от случайной потери данных.
- Удаление тары — намеренная операция, требующая сначала
  вынести пробы.

**Где:** `backend/apps/samples/models.py`.
**Статус:** ✅ действует.

## 2. Что не делаем и почему

- **Не используем `SampleParts`.** Разделение — вне WMS.
- **Не храним две колонки для Н/З.** Не масштабируется.
- **Не заставляем лаборатории использовать наш формат.**
- **Не переклеиваем старые этикетки.**
- **Не используем закрытые лицензии в ядре.**
- **Не ставим PostgreSQL или Docker Desktop нативно.**
- **Не используем SQLite для разработки.**
- **Не создаём кастомную модель User.**
- **Не используем Django fixtures для seeds ролей.**
- **Не запускаем Django-команды через кнопку «Run» в VS Code.**
